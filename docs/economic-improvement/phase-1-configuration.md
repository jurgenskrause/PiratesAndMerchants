# Economic Improvement configuration, Phase 1

Base commit: `5430506ff7a0deb9d9111fce48219b5ba680f731` (`economic-improvement` after Phase 0). World configuration revision: **0** by default; serialized snapshots carry their own revision and format version **2**.

## Source contract

The authoritative 41 `opening.*` definitions are in `dist/data/configuration_definitions.json`. The existing registry supports booleans, bounded integers and enumerated string choices; no new configuration type is needed. The source schema in `dist/data/catalog.schema.json` bounds enum option lists and requires nonempty definitions. `node scripts/compile-catalogs.mjs` validates source catalogs/defaults then regenerates `dist/data/catalog-bundle.js`; add `--check` to fail if stale. The generated browser bundle is 111,148 bytes versus 96,226 bytes at the base commit, an additional 14,922 bytes uncompressed. The browser and worker already consume revisioned world snapshots; neither has yet been changed to use this opening section.

| Group | Defaults and validation |
| --- | --- |
| Mode and participants | `opening.enabled=false`. British and Spanish enabled, French and Pirates disabled. At least two nationals must be selected. Pirates do not count. |
| Founding counts | Two colonies per faction; one crown and one small per national; two small per Pirate; one industry per colony. A national crown has one warship and two merchants, a national small colony has one merchant, and each Pirate colony has one ship. These are fixed-range settings for the agreed opening, present in snapshots for later consumers. |
| Docks and vessels | Crown `deep_water_quay` and `FIRST_RATE` (catalog Man-of-War), with `BRIGANTINE` and `SCHOONER` merchant defaults. Small colonies use `small_pier` and `SCHOONER`, with `BRIGANTINE` as a compatible alternate merchant class. Pirate class ID `CORSAIR` is reserved by the opening contract but has no catalog vessel yet. Unknown/unsupported enum choices, incompatible berth sizes and incorrect vessel roles are rejected. |
| Industry policy | `foundation_three` names the required sawmill, iron mine and cotton plantation coverage. Sawmill is not yet registered; activating the new opening fails clearly until Phase 2 delivers it. |
| Finite founding grants | Per-faction treasury 5,000 gold; crown port 500 gold; small port 250 gold; bootstrap 200 Wood, 80 Iron Bars and 0 Cotton. These are configuration proposals only: no grant or stock is created in 1.1. Phase 6 must specify ownership and reconcile each grant. Negative values are rejected. |
| Shipyard | Small/medium/large minimum population 100/300/600; Wood 40/100/200; Iron Bars 0/40/100. Thresholds must not decrease by tier. They are not construction recipes until Phase 9. |
| Anchorage | Minimum/preferred/maximum coast distance 2/5/12 world units; minimum depth 6. Distance ordering and numeric bounds are validated; actual clearance is a runtime concern. |

All settings are world-scoped and apply to a new world. The four participation toggles are marked user settable for the later world-generation selector. The other settings remain developer-owned. The accepted `CORSAIR` enum token is a documented future identifier; choosing it cannot activate Pirate founding until the actual Pirate vessel is registered. Faction placement and island capacity are not inferred from these settings. Phase 3 will reject map-specific impossible combinations.

## Compiled settings and route

`compileWorldConfiguration` produces a deeply frozen `opening` section with participants, colony/dock/fleet choices, policy, funding, tiered shipyard gates and anchorage. It carries the snapshot revision and has no UI defaults of its own. The existing generation UI's developer configuration panel renders enum choices as select fields and validates the selected values before storing them. Applying a world setting increments its revision and disables Simulate until a newly generated world carries that revision. Runtime requests for opening edits return the existing `new_world` boundary; simulation restart cannot activate them against an old map.

`world-scenario.js` defines `normal` and `legacy_benchmark`. Normal generation resolves the user-selected world snapshot. Both benchmark buttons use `legacy_benchmark`, which always resolves catalog defaults at revision 0, irrespective of developer selections. The generator worker reconstructs the immutable snapshot, validates the scenario, and returns both in the world. The main thread verifies the response against the request, including revision and all values, before accepting it. `MerchantTraffic` sends the same world scenario and snapshot to the simulation worker; that worker reconstructs and validates again, and rejects benchmark configuration requests. The normal Simulate button cannot reuse a benchmark-generated world. This isolates the old 50-merchant, 1×/20×, 60-second recipe without switching normal startup to the new economy.

Format-1 world snapshots from before this update may omit `opening.*` settings. Reconstruction fills **only** those missing keys from current catalog defaults, retains the old revision, and produces a complete format-2 snapshot. Missing non-opening settings, unknown fields, and incomplete format-2 snapshots still fail. Local developer selection storage remains version 1 because it stores overrides rather than a complete world snapshot; defaults fill new keys on load. There is no save-game migration claim.

## Verification and limits

Commands: `node scripts/compile-catalogs.mjs --check` and `node --test tests/economic-improvement-phase0.test.mjs tests/economic-improvement-phase1-config.test.mjs tests/economic-improvement-phase1-routing.test.mjs`. At Phase 1 completion: 16 focused tests pass, 0 fail. They cover snapshot roundtrip, two-national selection, ID and bound rejection, catalog-backed berth compatibility, gated unimplemented dependencies, prior seeded generation/dock/account invariants, benchmark recipe sentinels, asset paths and source/bundle parity. Phase 1.2 also checks deep freezing, format-1 migration, stale requests and real generator/simulation worker handlers at density zero. `git diff --check` passes. The static `dist/` deployment has no transpile step. No browser/WebGL test was run here; the README's named suites remain absent.

The fixed world and simulation benchmark map/ship/speed/duration recipes are unchanged. [One Node handler comparison](phase-1-node-comparison.json) with identical geography (32: 0 ports/0 industries; 128: 23/25; 512: 377/382) recorded worker generation at 45.25, 251.15 and 2,775.33 ms, versus the Phase 0 single-pass 24.21, 185.71 and 2,216.01 ms. These increases, including roughly 25% at 512, are an observed cold-run regression, not evidence that config routing caused it: single-pass container timings vary and the new checks happen before the worker timer starts. V8 heap after each map was 12.27, 13.80 and 18.62 MiB, compared with 13.43, 14.15 and 13.36 MiB in Phase 0; resident/external memory was unavailable. No new browser frame, GPU, or simulation tick comparison was run; the fixed browser reference remains the user's earlier Brave report in the Phase 0 document. The new route's effects on browser runtime timing remain unmeasured.

Normal gameplay still follows the legacy opening because `opening.enabled` defaults false and cannot pass prerequisite validation until the sawmill is registered. Phase 1 is complete only when its PR merges into `economic-improvement`.
